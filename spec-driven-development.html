What is a Spec?

There's no single definition — but Joel Spolsky distinguished two types that are both relevant in SDD.

📋

Functional Spec

  • Describes system behavior from the outside
  • Persistent and referenceable
  • Updated when the need arises
+
⚙

Technical Spec

  • Architecture, data models, APIs
  • Covers constraints and trade-offs
  • Aimed at the implementer

Different frameworks use different names, e.g. Product Requirement Documents (PRD) ...

Motivation Reasons to Consider SDD
Reality Check

Reasons to consider SDD

⏳

Enable long-running sessions

Specs give agents a detailed instruction set, and agents quiz you upfront — they run longer autonomously and don't need babysitting.

🌀

Avoid the iteration time trap

Iterating with vibe coding towards a solution works, but often leaves dead code and misfit architecture behind. Upfront specs reduce rework by getting direction right early.

🚧

Prevent misinterpreted intent

Vague prompts lead to confidently wrong output. Specs make intent explicit — no guessing.

“Bad specs produce bad code at scale.” Thoughtworks — Future of Software Engineering
🤝

Standards & Communication Base for Stakeholders

When specs become the source of truth, they serve as both an implementation guide and a standard / contract between stakeholders.

Best Practices Best Practices
What Works

SDD best practices

📁

Version your specs

Keep specs in the repo alongside code. Remove temporary planning artifacts.

🚦

Spec before change

Always add or update the spec first — then implement. And read/review them ;-)

🔀

Stick to PR best practices

Structure changes into reviewable PRs. Focus review on specs and architecture.

🎯

Right granularity

Not everything needs a spec. Match detail level to complexity — skip trivial items.

🔄

Iterate on spec

Refine with AI before implementation, then keep evolving the spec afterwards.

🧪

Include test criteria

Every spec defines how to verify success. Derive tests from it (e.g. e2e with Playwright).

🔍 Drift Detection in both directions

Code evolves, specs go stale. How do you detect when implementation drifts from the spec?

02

👥 Inter-Team Collaboration

Specs live per repo today. When multiple teams co-own a feature, who owns the spec? How do you align across boundaries?

03

📦 Specs across Multi-Repos

A single feature may span services, frontends, and shared libraries. Keeping specs consistent across repositories is unsolved.
